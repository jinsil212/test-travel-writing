# 우주와나 실험 — 분업 운영과 단계 관문

2026-10-02 사용자 승인: 기존 기준을 살리면서 기획·제목썸네일·도입·본문을 개별 에이전트로 분리하고, 앞 단계 통과 후 다음 단계로 진행한다. 적용 범위는 이 실험 폴더뿐이다.

## 기준과 수정 범위

- 이 폴더 밖의 원본 우주와나, 상위 공용 지침, 레전드열전·조선역사 실험을 수정하지 않는다.
- 공용 `_대본지침서.md` 사본, 채널설정, 실제 사용자 발언과 수정 전후 문장은 유지한다. 역할 문서는 담당 배정과 실행 계약이며 원문 조항을 대체하지 않는다. 기존 전체 정독 의무도 유지한다.
- 기존 경로 안내와 새 운영 절차가 충돌하면 이 테스트의 최신 사용자 승인과 이 문서의 역할 배정이 우선한다. 세부 내용 기준은 기존 원문을 적용한다. 이전 파일에 있는 원본 절대 경로는 읽기 참고이며 쓰기 대상이 아니다.
- 합격원고의 말투·설명·전개를 사용한다. 롱폼 분량·챕터 수를 미드폼에 가져오지 않는다. 과거 과학 사실은 재확인한다.
- 사용자의 확정 문구·도입은 그대로 유지한다. 오류가 있으면 문제와 최소 수정안을 해당 선택 단계로 반환한다. 조용히 변경하거나 문제를 면제 통과시키지 않는다.
- 새 피드백을 반영할 때에는 이 폴더의 공용 사본/채널/이번 편 중 해당 범위에 반영하고 충돌 조항을 함께 고친다. 원고 수정·검증과 지침 저장을 구별한다.

## 에이전트 역할과 실행

총괄 + 조사 + 기획 + 제목썸네일 + 도입 + 본문클로징 + 독립검수 역할을 둔다. 역할별 파일은 `지침/에이전트/`다. 제목과 썸네일은 한 에이전트가 한 조합으로 만든다. 기획에서 질문·가안·끝에서 줄 답을 세우고 포장 담당이 같은 방향 안에서 발전시킨다.

동시 실행은 총괄 포함 4명 이내다. 단계마다 필요한 에이전트를 순차 배정하고 완료한 결과를 파일로 넘긴다. 전 단계의 작성 담당이 다음 담당의 역할을 대신해 자기 초안에 자기 통과를 주지 않는다. 최종 사실 검수와 흐름 검수는 서로 다른 에이전트로 병렬 수행한다. 에이전트 생성 도구 자체가 이 문서만으로 자동 실행되는 것은 아니다. 총괄이 실제로 생성·전달·수집한다.

배정 시 반드시 전달: 역할 지침 경로, 이번 편 요청, 실제 에이전트 ID, mode, 현 단계, 읽을 원문과 범위, 입력 파일 해시, 이번 단계 산출물, 통과 조건, 쓰기 범위. 제출 시 사용한 원문 구절·누락/한계·파일 경로를 회수한다. 실제 ID를 기록하고 가상의 역할명을 실행 증거로 쓰지 않는다.

## ASK와 AUTO

기본 ASK. 이번 시스템 개편 승인은 특정 편의 AUTO 작성 위임이 아니다. ASK는 기획, 제목썸네일, 도입 선택에서 실제 사용자 결정을 기록한 뒤 진행한다. 사용자가 일부만 위임하면 그 범위만 적용한다. CLI의 mode는 전체 실행의 ASK/AUTO이며 부분 위임은 ASK를 유지하고 해당 선택의 실제 위임 발언·총괄 선정 이유를 함께 기록한다. 현재 CLI는 ASK에서 source=user와 결정 발언을 요구하므로 위임 근거를 사용자 발언으로 기록하고 선정 주체는 설명에 구별한다.

AUTO는 사용자 명시 위임 시에만 설정한다. 내부 비교·선정하고 PASS를 얻어 계속한다. 추가 사용자 승인 관문을 만들지 않는다. 작업자 선정과 사용자 합격은 다르다. 정상적인 선택 대기나 자료 확보 실패를 완성으로 보고하지 않는다.

## 하나의 약속을 넘기는 문서

기획 `plan.md`에 쉬운 말의 배경/사건/핵심 질문/줄 답, 클릭 이유, 넣을 것·뺄 것, 상세 흐름, 포장 가안과 공개/유보 범위를 쓴다. 포장 `package.md`에는 선정 제목·썸네일을 원문 그대로, 같은 질문을 향하는 근거, 첫 문장이 받아야 할 기대, 본문이 줄 답과 관련 claim ID를 적는다. 도입 담당과 본문 담당은 이 내용을 바꾸지 않는다. 변경이 필요하면 실패 원인에 맞는 이전 단계로 반환한다.

## 단계와 통과 조건

| 단계 | 작성 역할 | 산출물 | 독립 검수 필수 기준 |
|---|---|---|---|
| research | 조사 | research.md | sources / uncertainty / briefing |
| plan | 기획 | plan.md | question_answer / scope / flow / benchmark / length_material |
| package | 제목썸네일 | package.md | user_examples / candidate_coverage / same_promise / standalone / image_prompts |
| opening | 도입 | opening.txt | benchmark_before_writing / weakness_not_copied / same_promise / beginner / transition |
| part_01… | 본문 | part_01.txt… | necessary / facts / connection / language / new_value |
| closing | 본문 | closing.txt | promise_paid / new_meaning / no_repetition |
| final | 총괄 조립 | final.txt | 사실: claims_sources / numbers_conditions / future_hypothesis / image_sources; 흐름: promise_chain / beginner / no_tangents_repetition / natural_language / latest_requests / length |

위 영어 키는 도구용이며 의미와 원문 조항은 역할 지침에서 확인한다. 기획·포장·도입의 후보 수, 프롬프트 3개 등 명시 요구를 실제 산출물과 대조한다. 글자 수만 맞거나 파일이 있다고 통과시키지 않는다. 연구 근거는 주장 ID / 실제 주장 / 원자료 URL·날짜·확인 구절 / 연구 단계·조건 / 신뢰도·상충 자료 / 대본에 쓸 범위로 연결한다.

NA는 실제 적용 범위와 이유를 남기고 실제 문서 구절도 연결한다. 핵심 질문, 약속 회수, 초보자 이해, 사실 확인, 최신 사용자 요구처럼 항상 적용되는 기준을 NA로 면제하지 않는다. 코드가 NA의 타당성을 의미적으로 판단하지는 못하므로 총괄이 확인한다.

최종 4000자 이상(공백 제외)은 400자/분에서도 10분을 확보하려는 보수 추정 관문이다. 음성 실측은 아니다. 상한이 있으면 300자/분에서도 그 상한 이내인지 검사한다. 추정 범위가 요청에 안 맞으면 기획을 수정한다. 도입 비율·질문 밀도·전환 위치 등은 진단 참고값이다. 기능상 적절하면 수치 이탈만으로 실패시키지 않는다. 곁가지와 불필요한 국면은 검수에서 지적하고 작성자가 삭제·재구성할 수 있다.

## 실제 저장 흐름

새 작성은 `실험/에피소드/<실행이름>/`에서 한다. 기존 `우주와나/원고/`는 비교 자료로 보존한다. 입력 초안과 검수 JSON은 `실험/입력/`에 파일 도구로 만든 뒤 관문 CLI로 등록한다. 한 실행의 파트 수는 초기 기획에 맞춰 정한다. 범위·파트 수·요청이 바뀌면 새 실행 이름으로 시작해 해당 근거를 재사용하되 재검토한다.

1. 실제 요청 원문과 실제 배정 ID 목록을 입력 폴더에 저장한다.
2. `init`으로 실행을 초기화한다(새 이름; 기존 실행 덮어쓰기 금지).
3. 담당은 필수 원문·선정 견본 전문을 읽고 `read-record`로 실제 구절과 이번 편 적용 설명을 등록한다.
4. 총괄은 `check`로 앞 단계 통과를 확인하고 담당을 배정한다. `check`의 ready는 작성 준비 조건을 충족했다는 뜻이며 현재 단계가 통과한 것은 아니다.
5. 담당은 견본·합격원고·피할 약점·이번 단계 목적을 `prepare`로 먼저 기록한다. 뒤늦게 원고에 맞는 견본을 붙이지 않는다.
6. `write`로 산출물을 저장한다. 도입·파트·클로징은 낭독문만; 화면·출처·검사 근거는 별도 문서/JSON이다.
7. 독립 담당은 실제 산출물 해시·검사별 실제 구절/이유·미해결 목록을 작성하고 `review` 등록한다. FAIL 보고도 저장하지만 다음 단계는 PASS만 허용한다.
8. FAIL이면 담당이 수정, prepare/write/review를 재실행한다. 원고·참고자료·선행 결과·선택·지침이 바뀌면 관련 통과가 무효화된다.
9. 모든 파트/클로징 PASS 뒤 final 준비, `assemble`로 조립한다. 최종 사실·흐름 검수 둘 다 PASS여야 완성이다. final을 직접 편집하지 않고 문제가 있는 원 파트로 돌아가 수정한다.
10. 최종 status와 전문 재확인 후 제출한다. 실제 TTS/업로드/외부 보드 등록은 그 작업 요청 범위에서 실행한다.

CLI 상세는 `도구/사용법.md`. 판단/기록용 템플릿은 `지침/양식/`. 빈 템플릿을 복사한 것만으로 통과했다고 보고하지 않는다.

## 훅과 실제 활성화 상태

`도구/hook.py`는 SessionStart/SubagentStart에서 역할·관문을 알리고, PreToolUse에서 단계 파일 직접 편집 및 불투명한 셸 실행을 차단한다. 허용된 CLI가 선행 PASS와 실제 버전 연결을 확인한다. Stop은 활성 AUTO 실행 미완료를 한 번 차단하며 무한 루프는 막는다. ASK의 선택 대기는 차단하지 않는다. 이 종료 장치만으로 미완료 결과를 완성이라고 보고하는 것을 기술적으로 완전히 방지할 수는 없다.

Codex용 `.codex/hooks.json`, Claude용 `.claude/settings.json`을 각각 준비한다. Codex는 활성 프로젝트 설정 계층과 훅 정의의 신뢰 검토가 필요하다. 현재 프로젝트 밖 채팅에 파일을 만들었다고 바로 활성화되지 않는다. 이 폴더를 프로젝트 작업 위치로 사용하고 `/hooks` 등 지원되는 관리 화면에서 신뢰/실행 로그를 확인한 뒤 활성화 완료로 기록한다. 상위 저장소/사용자 전역 설정을 변경하지 않는다. 중첩 폴더 설정이 활성 계층으로 로드되지 않으면 이 폴더만 지정한 별도 실행 구성이 필요하다.

공식 설명: https://learn.chatgpt.com/docs/hooks

ID·사용자 발언·정독 기록은 총괄이 실제 실행과 대조하는 증빙이다. 문자열·해시·인용 검사만으로 사람의 승인 진위, 전문 이해, 출처의 사실성, 원고의 재미가 증명되지는 않는다. 훅은 보조 장치이며 모든 실행 경로를 감싸는 보안 경계가 아니다. 원고 품질은 독립 내용 검수와 사용자 평가로 판단한다.


## 기존 세부 지침 역할별 분리 — 2026-10-02

`지침/세부지침/분리_안내.md`의 배정에 따라 공통 원문과 각 담당 원문 묶음을 전문 읽는다. 출처는 기존 공용 지침·채널설정·수정선택 사례·원고쓰는법·검수기준서 5개다. 기존 원문 전문·이번 편 견본 전문 정독 의무도 유지한다. 다른 채널 전용 조항만 배정표에 이유를 남겨 제외한다.

사실 검수는 `07_사실검수.md`, 단계/흐름 검수는 `08_흐름검수.md`로 분리하며 둘 다 `06_독립검수.md` 공통 정책을 읽는다. 관문은 담당 원문 묶음의 열람 누락, 원문/묶음/배정 변경을 차단한다. 최종 흐름 JSON에는 기존 6키와 `criterion_01`~`criterion_25` 25개 개별 검사가 모두 필요하다. 각 키에는 마지막 최종 원고의 실제 구절·위치와 판정 이유를 둔다. 위치/비중 수치는 진단이며 숫자를 맞추려고 내용·문체를 왜곡하지 않는다.

원문이나 배정이 바뀌면 `도구/지침_분리.py`로 분리본을 갱신하고 `--check`로 정확히 대조한 뒤 새 실행을 시작한다. 파일 열람/해시 일치는 전문 이해·원고 품질을 자동 보증하지 않는다.

단계 검수의 read_review 기록에는 해당 작성 역할의 실행 계약과 세부 원문도 포함해야 한다. 최종 사실/흐름 읽기·검토는 병렬 가능하며, 판정 등록은 final_fact PASS 등록 뒤 final_flow를 등록한다. final_flow의 `fact_review_reference`는 사실 담당 ID·같은 final 해시·현재 사실 receipt 해시·claims_sources/numbers_conditions/future_hypothesis 참조 키를 포함해야 한다. 검사표17/20을 흐름 담당이 단독 사실 통과로 처리하지 않는다.
